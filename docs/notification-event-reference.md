# Notification Event Reference Guide

This document provides a comprehensive technical reference of all notification events emitted, processed, and stored across the system. It covers the trigger locations, payload definitions, notification names, message templates, and recipient logic.

---

## 📖 System Overview

All notifications are processed centrally on the backend through the `NotificationService` in [notification.db.modules.ts](file:///c:/Dhanraj%20Pimple/RJFintech_backend-18054219e9ad907eb97fa42a6c477078f189fb53%20(1)/RJFintech_backend-18054219e9ad907eb97fa42a6c477078f189fb53/src/backend/modules/notifications/notification.db.modules.ts). The frontend or middlelayer clients retrieve notification feeds via Server-Sent Events (SSE) or HTTP API endpoints defined in the middlelayer's [notification.controller.ts](file:///c:/Dhanraj%20Pimple/RJFintech_backend-18054219e9ad907eb97fa42a6c477078f189fb53%20(1)/RJFintech_backend-18054219e9ad907eb97fa42a6c477078f189fb53/src/middlelayer/controllers/notification/notification.controller.ts).

### Core Fields in a Notification Payload
- **Reference Type (`referenceType`)**: The domain entity classification (`COMPANY`, `USER`, `ORG`, `WORKFLOW`, or `null`).
- **Notification Type (`type`) / Event Type**: The operation type (`INITIATE`, `APPROVE`, `REJECT`, `ONBOARDED`, `MODIFICATION`, `ACTIVE`, `INACTIVE`, `ARCHIVE`).
- **Name (`name`)**: The title of the notification displayed to the user.
- **Message (`message`)**: The descriptive body text.
- **Recipient User IDs (`recipientUserIds`)**: The list of target user IDs to receive this notification.

> [!NOTE]
> All notification recipients are filtered to active members of the company and automatically merged with SaaS administrators (`SAAS_ADMIN`) and Corporate administrators (`CORP_ADMIN`) depending on the context.
